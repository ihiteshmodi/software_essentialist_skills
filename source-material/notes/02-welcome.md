## Core ideas
- Most developers don't invest in themselves; the landscape is "kind of a mess" -> confusion, frustration, reading tons of books without clarity.
- **Main goal:** write scalable code in any context, regardless of language/framework/platform/front end/back end/greenfield/existing project/new feature.
- Rely on the **80/20 of software design, testing and architecture** -> confidence to know what to do in different scenarios.
- It's about "becoming a professional developer and learning the things all professional developers know," compiled into **12 essentials**.
- Target audience: front-end, self-taught, back-end, entrepreneurial devs, or any dev lacking clarity.
- Move from lacking clarity to so much clarity you're "probably bored" — and boredom (here) is good because **it lets you tap into creativity instead of stress**.
- Foundation built on top of: domain-driven design, test-driven development, behavior-driven development, object design, architectural principles, architectural styles.
- **Skills require practice:** "drill it, drill it, drill it" — lots of code and lots of design.
- **Design feels non-linear**: having to start over from scratch is a sign of progress; you have to make mistakes, tear it apart and start again — this is what makes design feel like an art form.
- Skill is developed like muscle: stress it consistently, over and over.

## Named frameworks / mental models
- **Skill-as-muscle model** — purpose: set expectation that competence comes from repeated stress/practice; when to use: when design attempts fail and you feel like starting over.
- **Clarity -> boredom -> creativity** — purpose: clarity removes stress; with clarity, creative capacity opens up.

## Definitions
- **SolidBook** — Khalil's first attempt at what became the Software Essentialist mentorship training and then this course; final version to be called *Software Essentialism*.
- **Early adopter phase** — V1 build-out phase of the course (weekly videos, feedback -> V2 -> V3 before official launch).

## Rules & heuristics
- Do what's instructed and apply it; expect to write a lot of code and do a lot of design.
- Treat restarting a design as progress, not failure.
- Leave feedback; use community channels.

## Anti-patterns / mistakes called out
- Not investing in yourself as a developer.
- Reading tons of books / "doing all kinds of weird stuff" without a coherent path.
- Treating a failed first design as a reason to quit (implied).
