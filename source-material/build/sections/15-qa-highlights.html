Mar 14, 2023: FDD (Figma-Driven Design) L84

First day of the early-adopter cohort. Khalil draws architecture and writes TypeScript straight onto a Figma canvas. “FDD” is a joke, not a method. The session opens with a tech lead about to rewrite an MVP as microservices with two backend devs.

Top insights

  • An architecture choice is a theoretical guess that multiplies physical guesses (observability across deployables, messaging infra). It must be “solidly justified” against potential negative value. Fewer components → fewer guesses, which is why serverless is popular. L84
  • Extensibility comes from first principles, not microservices: vertical slicing + horizontal decoupling. A modular monolith (Vaughn Vernon, Strategic Monoliths) can give you the same. L84
  • Core vs infrastructure code: classify code by what it touches (DB, file system, network, system clock, random generator), not where it comes from. new Date() and Math.random() are infra, so wrap them behind a clock contract. L84
  • Everything in the Express controller = anemic domain model. With no layers you can only black-box test, and E2E only allows result verification. Edge cases like “deactivated, rejoins → welcome back” become nearly impossible to reach. L84
  • Three verification types: result (palindrome), state (checkers, found via wishful thinking getCurrentPlayer()), communication (use case ↔ injected contracts). Communication is “the hardest one” but gives the most valuable tests. L84
  • The repository is the adapter. An interface is a role; FirebaseUserRepo and SequelizeUserRepo are actors that play it. CreateUser depends only on the role. L84
  • Abstract → concrete spectrum: start with an interface. Move to an abstract class only after the rule of three, and pair it with YAGNI. “This game is really just fighting your own self.” L84
  • Gherkin as training wheels for application-level-3 use-case tests, where setting up “the state of the world” is complex. L84
  • External services (Stripe, PayPal, mail) get the minimum integration code wrapped in a service. A capability you buy “becomes pretty much that bounded context”. L84
  • Essentialism’s steps (explore/evaluate the phronimos → eliminate → execute) are how Khalil distilled the 12 essentials. L84

Best Q&A exchanges

Q: Is microservices a good decision for a team of two backend devs? It’s a theoretical architecture guess that forces many physical guesses you may not be aware of. Justify it against negative value first. Vertical slicing and horizontal decoupling in a modular monolith give the same maintainability and extensibility. L84
Q: Is it fair to say infra code = packages you install? “Not completely fair.” An npm library that only returns a string is core. Express is infra because it opens a port and touches the network. L84
Q: Navigating interfaces is painful because I can’t ctrl-click to implementations. Three-part fix: slice features into feature folders, use cohesive naming and folders, and follow the layered rules so you always know use cases reference interfaces. L84
Q: Is a user an aggregate? “Depends.” Talk about the data and behavior each feature needs instead. That exposes what an aggregate is and isn’t. L84
“It’s not about where it comes from it’s about what it touches.”L84
“The repository is the adapter... it is a role to be played.”L84
“My goal here is for everyone to become their own coach to make myself redundant.”L84

Where this is covered: Horizontal Decoupling · Subject/System Verification · Verification per Guess Point · Contract Tests & FakeClock · Strategic Design · Modular Monolith vs Microservices · Roles & Actors

Mar 31, 2023: Mastery Foundations L85

A preview of the Mastery Foundations section, which sits between the “stay in the game” mindset material and the physical guess points. It’s mindset-heavy (“It’s extremely abstract”), followed by course logistics.

Top insights

  • Right action: work is full of quantum moments, decisions that send you down different paths. What you do in them depends on what you currently value. L85
  • Phases of craftship: code-first → best-practices-first → pattern-first → DDD-first → responsibility-first → value. At the deepest level, software development is a game of value won with the feedback loop. It’s non-linear, so there are “no silver bullets”. L85
  • Mastery process: observe & evaluate → eliminate → execute. Khalil’s elimination produced the 12 essentials, taught as a “straight line” instead of wandering topic to topic. L85
  • Value creation system, left → right: theoretical guess points (problem, solution, architecture) come before physical ones. Scoring = shipping value; negative value = bugs. L85
  • Zero validated theoretical guesses? Don’t run multi-loop TDD at every guess point. Push one guess through fast, then “start playing defense” with tests at the physical level. L85
  • Platform strategy: shared infrastructure (known deploy, architecture, tested services) lets later features skip guess points and score faster. L85
  • Tools belong to guess points: big-picture event storming → problem; tactical event storming → solution; impact mapping and user story mapping → theoretical guess points. L85
  • Any question = one metaphysical essential + one physical/theoretical essential. “How do I do transactions in use cases?” = abstraction design + temporal decoupling. L85
  • Small guesses applied to the course: MVP in text first (video feedback loops are too long), with opt-in access to rough “prod” content. L85

Best Q&A exchanges

Q (Rohan): I’m confused. What should I do now? Ask a goal-based question: “What is your current goal?” Developers often don’t know what they need to know. The course is the straight-line path that came out of observe → eliminate → execute. L85
Q: Should we TDD at every guess point? Not with zero theoretical guesses validated. Push one artifact through fast and add tests afterwards. With a platform in place you can skip some guess points altogether. L85
Q: Where do event storming, user story mapping and impact mapping fit? In the theoretical guess points. Knowing which guess point each tool serves is a “massive simplification”. L85
Q: What’s the best way of letting go of old paradigms? It’s painful (Luigi went from code-first to using RDD in interviews). Structure it with milestones and checkpoints so you don’t get stuck “in the void”. L85
“Right action really, truly, is based on what you currently value.”L85
“It’s less about the tool. It’s more about the inputs, outputs of the system of creating value.”L85
“The problem that a lot of developers have is they don’t even know what they need to know.”L85

Apr 22, 2023: First Milestone Review & Intro to the Stateful Guess Point L86

The TDD content had just moved from the book into the platform. Despite the title, no milestone code is reviewed. The session covers FA²STR at any level, how to organize code, and a long introduction to state machines, invariants and fixtures.

Top insights

  • FA²STR is an input → output tool usable at any level of abstraction, from a pure function up to a job queue. For simple problems it happens in your head. L86
  • “n loops”, not an nth-layer loop: start at any level, run FA²STR, emergent design surfaces new constructs, and you drill in again. You can shortcut levels depending on “the score of the game”. L86
  • Stack theoretical guesses (architecture, platform, process) so physical guesses go faster. That’s the case for strategic monoliths and good platforms. L86
  • Organize code from developer use cases (find/add/remove/change/extend/understand a feature, run its test) rather than folder conventions. The README should show them within ~10 seconds (Don Norman’s discoverability; Cockburn’s use cases). L86
  • Problems are stateful. The hand-washing-clothes state machine is built backwards from the end state. Invariant = rule = business logic; it blocks invalid transitions like “gathered clothes → clothes clean”. L86
  • States and events are two sides of one coin, and the purpose of encapsulation is “to protect the way the model changes”. L86
  • Fixture = initial state. Don’t act out 20 chess moves per test. Use GameBuilder.fromCommonGameState(GameStates.theMostBrutalGameEver). L86
  • “Planning is a lie”: you have plans, not a plan. Give estimates, not dates. Don’t push the team to adopt named techniques; value-first is about you deciding better. L86
  • Tracer bullets / walking skeleton show how fast you actually work, which makes estimates better. L86

Best Q&A exchanges

Q: Is there a particular way to organize code? Start from the developer role’s goal and the actors and impacts (impact mapping), then list developer use cases. Make them discoverable: the README first, then module folders that reveal features. L86
Q: What is a fixture? The initial state. The line-by-line chess checkmate test was refactored live into a builder with named, team-known game states. L86
Q: How do I fit FA²STR into team planning and meetings? “Planning is a lie… You have plans.” Many practitioners use these techniques without naming them, so don’t evangelize. Use them to make better decisions yourself. L86
“It doesn’t matter where you start… you need to drill in with several loops.”L86
“What is the purpose of encapsulation? To protect the way the model changes.”L86

May 5, 2023: The Most Valuable Ideas, Frontend Architecture & the Ideal Developer Workflow L87

Khalil front-loads the “game-changing” ideas so students don’t wait for them: the stereotypically testable architecture and the ideal developer workflow from GOOS. Much of the Q&A applies them to the frontend.

Top insights

  • There is one stereotypically testable architecture on frontend, backend and desktop; only the terminology changes. Place any tool (Next.js, Nest.js, Redux, NgRx) by asking which responsibility it handles. Find problem points by measuring the gap to it. Source: Object Design (Wirfs-Brock). L87
  • The guess points exist to let you write tests strategically: stateless (1), stateful (2), application (3, “quite literally life-changing”), outgoing adapter (4), system/E2E (5), with incoming adapters mentioned alongside as “four and six”. L87
  • Ideal developer workflow (GOOS double loop): once per project, Find/Architect/Automate and deploy a walking skeleton. Per feature, write a failing E2E acceptance test → a failing level-3 use-case test (~80% of time) → the remaining ~20% on adapters, E2E pass and UI hookup. L87
  • If you need to start React to test your features, React is doing the coordination. A library becomes a framework when it coordinates and controls. A plain Presenter (read) and Controller (write) let you test the whole app without React or the API. L87
  • One acceptance test per feature, shared by frontend, backend, mobile and desktop (Dave Farley). Each team validates it its own way. L87
  • Verification per guess point: stateless → result; stateful → state; application → adds communication (the only place for it); E2E → result only. State or communication checks at E2E are “bad practice”. L87
  • Frontend state flow: API-client cache → global state → domain + view models → component initial state → local component state. Interactions go through the controller. L87
  • Redux mapped to the stereotype: store/reducer = cache/gateway, selectors = reactive queries that belong in the presenter (never in component files). Use-case tests never mention Redux. L87
  • Domain objects are for writes only. Queries go straight to the store and return the simplest shape, which avoids “mapper hell”. L87
  • The answer to “stop mocking”: handwritten spies and in-memory repos (turned into builders), kept in sync with the real ones by contract tests. L87

Best Q&A exchanges

Q (Tim): Does the first deployed slice have to be the first feature? No. That’s the walking skeleton (via tracer bullets). It can be as small as getting data from the DB onto the screen. The point is to surface infra problems before feature work. L87
Q (Daryl): How do I handle “then I get an email” at E2E when frontend and backend deploy separately? There’s still one acceptance test. E2E does result verification only (e.g. a 201), and email can be a no-op there. Verify the email at the application level with an email spy. A provider sandbox only saves cost; it doesn’t prove delivery. L87
Q: How do controller tests work with Redux/NgRx? Read the docs for its doings and knowings and map them to stereotypes. Selectors live in the presenter. Test cache hydration separately as an outgoing adapter test. “Keep them separate.” L87
Q: Does DDD belong on the frontend? Yes for logic-heavy apps (a DAW, a drag-and-drop call-flow editor, a pedal-board chain). Daryl added that it also speeds up feedback because there’s no network round trip. L87
“If you want to test your features, if you need to start react, then react is doing the coordination.”L87
“You only ever have one acceptance test. You don’t switch the test for different environments.”L87

May 25, 2023 (Office Hours): Decoupling From Infra & the Stateful Domain Modelling Guess Point L88

The first “office hours”, where Khalil teaches live to get the tightest feedback loop. It starts from a student’s naive Express createUser (“a lot of missed concerns”, “no domain model”) and ends on aggregates and keeping the domain pure. The stateful guess point is renamed the Stateful Domain Modeling Guess Point.

Top insights

  • Two problems with a naive backend: (1) E2E tests don’t scale, because DB fixtures are complex and slow and the granularity is wrong; (2) the controller, app logic and business logic are fused. L88
  • Fix 1, dependency inversion: core code uses a persistence contract; the real DB and an in-memory fake both “play the role”. The same goes for a fake PaymentService instead of Stripe. L88
  • Fix 2, the application interface: all use cases composed into one pure object that the web server uses (the composition essential). L88
  • Incoming adapter tests only check that endpoints call the right use cases with the right parameters. They catch the “works in tests, fails when deployed” class of bug (e.g. CORS). L88
  • Avoid the word “integration” (“means so many different things”) and avoid packaging by infrastructure. L88
  • Nth looping (renamed from double looping): Student entity (L2) → FirstName/LastName value objects → level-1 validation. Level 2 uses state verification plus domain events to prove objects change for the right reason. L88
  • Aggregate = the minimum data needed to perform a command. Command-specific shapes (UserForEditUser) → rule of three → an abstract User. Can’t find the boundary? You’re doing too much in one command → temporal decoupling. L88
  • Transaction-script danger: a makePurchase that crashes between billing and the inventory update leaves an invalid state. Khalil hit this on the solidbook site, made worse by serverless cold starts. L88
  • Order of work: never make physical guesses before the theoretical ones are sorted. Problem → solution space (core/supporting/generic) → architecture (build vs buy) → physical. L88
  • The domain must be pure: no new Date(), Math.random() or setTimeout, so inject a clock. Frontends are connected domains too; React Router has its own domain layer. L88

Best Q&A exchanges

Q (Talib): Is my test structure right (acceptance tests on business logic, double-loop TDD)? Mostly. Fix the two problems with fakes plus an application interface. Then follow the ideal developer workflow: one production-like E2E, most tests at level 3, ~20% infra tests. L88
Q: Can the web server depend on use cases directly? Use incoming adapter tests with an application interface so the tests don’t have to configure every real use case. Daniel added: without it “you end up building your app within your framework”, and Khalil agreed. L88
Q: How do I design aggregates / aggregate roots? Include only the data a command needs to execute and check its rules (edit user doesn’t need the password). Event storming comes first, and it’s “non-negotiable”. L88
“An aggregate is the minimum amount of information required for you to perform a command.”L88
“You never want to be making physical guesses unless you have your theoretical guesses sorted.”L88
“The domain model needs to be super pure. It’s not allowed to know about system time.”L88

Where this is covered: Horizontal Decoupling · Composition · Aggregates · Event Storming · Temporal Decoupling · Ideal Developer Workflow

Jun 7, 2023 (Office Hours): Theoretical Guess Points, Aggregates, State Machines L89

Held after the theoretical content (problem, solution and architecture spaces) shipped. The theme: the hard part is the what. Most of the session is about aggregates as transaction boundaries and decoupling from time.

Top insights

  • The hard part of programming is determining the “what”, which is about language. Anxiety at work signals a lack of clarity. Write the process down first and execution “feels like typing”. L89
  • Information systems are state machines: one emits an event that triggers the next. Keep to one state change at a time within a context. L89
  • Events may branch across contexts (OrderPlaced → billing + email) but never into two paths in the same namespace. L89
  • Aggregate = transaction/consistency boundary, a level-3 (application) concept; entities and value objects are level 2. Test: if the system dies halfway through, is it inconsistent? L89
  • Relationships go by identifier. A playlist reorder uses a linked list (previous/next IDs), so one small transaction does the move and the rest is eventually consistent. L89
  • Applications force purposefulness: work from level 3 (developer boundary) or level 5 (customer boundary), or you’ll model dogs → owners → houses → cities forever. L89
  • Time is an application concern. Use a Clock role with SystemClock and FakeClock, kept in parity by a level-4 contract test that loops over both. L89
  • Why level 3 is hard: FA²STR’s find step must surface every responsibility there (time, repos, transactions, events, auth). That’s why the course teaches inside-out. L89
  • On AI: it “crunches down” decision-making logic, but you still need the inputs, outputs and goalpost it plugs into. L89
  • Laurent on slicing: a slice is a slice of value, not a technical slice. Technical enablers are chores. Ship behind feature flags and migrate incrementally (nullable column → required). L89

Best Q&A exchanges

Q (Lucas): Is finding the aggregate per event always a good approach? It’s the best way to find the required input. Khalil avoids the word “aggregate” while event storming and looks at inputs and outputs instead. After the process model, drop straight into level 3. L89
Q: Is an aggregate the same as a DTO? No. A DTO is data in a shape with no behavior. An aggregate is the data that must change together in one transaction. L89
Q: How do I handle time in the traffic-light / Pomodoro assignments? Time belongs to the application: a Clock role, a fake that fast-forwards an hour instantly, and a contract test against the real clock. L89
Q: What is a feature/slice? Laurent: the smallest shippable, usable result that solves part of the problem. Use user story mapping for value slices and event storming for developers. L89
“Information systems are just state machines.”L89
“It’s okay to mock... but just make sure you mock correctly... You want to create parity between what’s real and fake.”L89
“If you don’t have clarity on what matters, everything’s gonna seem like a threat.”L89

Jul 4, 2023: From Code-First to Best-Practice First L82

The course is restructured around the phases of craftship, and Khalil previews what best-practice-first will fix in code-first projects.

Top insights

  • Phases of craftship are the course spine. Guess points, FA²STR and the ideal workflow only make sense once you’ve climbed them. L82
  • Why the course is built incrementally: Khalil first wrote “thousands and thousands of pages of theory” up front. Now he adds foundational theory only when it’s needed. L82
  • Code-first problems: manual testing with curl, thinking in endpoints instead of features, and a DB installed on the local machine. L82
  • Debugging loop: if you keep changing something and it keeps failing (Dockerfile edits on a 30-second cycle), stop, zoom out, draw it, clarify responsibilities, then descend. L82
  • Role → goal → features → concrete examples → acceptance tests. DDD Forum reframed: a conference organizer wants an audience of DDD-curious developers to sell tickets to. L82
  • Acceptance test = shared executable spec for frontend and backend. Four layers: example → runner → test code → protocol driver (a page object on the frontend) → system. L82
  • Three test categories: acceptance (“does it do what the customer wants?”), unit (~80%), infrastructure (start/stop DB, web server). L82
  • Minimal pipeline (after Dave Farley): commit phase → release candidate → acceptance phase in a production-like environment → infra tests → deploy. L82
  • Architecture progression: view-controller-DB → service layer (four-tier, slim controllers) → pure application/domain core. Add a composition root and Docker for the dev DB. L82
  • Monorepo with frontend/, backend/, shared/ (acceptance tests, later DTOs). Each non-trivial frontend gets its own MVC with presenters. L82

Best Q&A exchanges

Q: One acceptance test for the whole app, or separate ones for frontend and backend? Write it so it can run on either side, as a shared executable specification. Run it against the backend, or end to end through a page-object protocol driver. L82
Q: Should “Then” be past tense, like an event? Usually (“order should have been placed”, “email sent”). Present tense is fine for UI experience (“I should now be logged in”). The hard rule is to describe the system the way the user interacts with it. L82
Q: Our team of three has strong product ownership. Which artifacts should we use? Role-goal (≈ impact mapping, feature injection), process modeling, user story mapping and example mapping. Documents are a side effect of shared understanding and go stale. Read BDD in Action or Specification by Example. L82
“You’re just so too deep into the how. What you need to do is stop, zoom out, draw it up front.”L82
“Never start a project without these four words clearly understood.”L82

Jul 27, 2023: The Walking Skeleton, Pipeline & Contract Tests L81

More restructuring: the DDD Forum build assignments become optional, and students apply the 4-layer E2E setup to their own work instead. The session ends with the definitive answer to “we’re only testing our mocks”.

Top insights

  • Developers do two things: improve existing features and add new ones. To improve, write a characterization test around the black box, then move in a layer and distill (Evans). Don’t rewrite from scratch. L81
  • New flow: code-first → testing basics → best practices (E2E backend with Docker → E2E frontend → walking skeleton → deploy → minimal pipeline → improve the design) → pattern-first. L81
  • Walking skeleton = tracer bullet. Khalil’s own mistake was writing all the pure core first, then hitting “all these weird CORS errors” on deploy. L81
  • Execution guess point: after users use the code, check the KPIs. That closes the loop back to the start of the value creation system. L81
  • Pipeline: commit phase (lint, build, unit tests giving ~80% confidence, package) → acceptance phase (staging + E2E) → production. Put tests in CI, not only in Husky hooks. L81
  • Six test levels via systems thinking: L6 incoming, L5 system, L4 outgoing, L3 app, L2 stateful, L1 stateless. “It is just all inputs and outputs.” L81
  • Test mix: E2E for the happy path plus one or two sad paths, then ~12–20 high-value tests with concrete examples, parameterized. L81
  • Library mocks only for trivial stubs (a logger). Stateful dependencies are indirect inputs, so use fakes covered by contract tests. L81
  • React hooks “really force you to completely mangle your code”. Use a plain observer store and extract a routing service. L81

Best Q&A exchanges

Q: Should these tests run locally via Husky? Devs can turn hooks off and push broken code, so run tests in the pipeline (GitHub Actions). A student’s rule, endorsed: fast things pre-commit, slow things in CI. The minimum is that you can deploy and the E2E tests run. L81
Q: When we mock the use case’s repo, devs feel “we’re just testing what we put into the tests”. That feeling is a symptom of missing contracts. Run one integration spec over every repo implementation, fake and prod, so if one breaks they all break. L81
Q: What if the repo has complex filters and aggregations that are hard to fake? Pull the filtering into its own abstraction or subdomain (e.g. search). If the DB does the heavy lifting, test the contract and “let the external tool do the external tooling”. L81
“You’re testing the contract, not the implementation.”L81
“If you could deploy, and if you can run the E2E tests, and the E2E tests run, you’re good.”L81
“Raise the level of abstraction of what it is you’re looking at to test.”L81

Aug 15, 2023: New Q&A Structure + Frontend Architecture 1 of 2 L90

This session introduces the new format: topics proposed in the office-hours channel and voted on. Frontend architecture beats high-value unit testing, and Khalil draws the whole frontend architecture on an iPad.

Top insights

  • Two mental models (feedback loop + abstraction), tied together by systems thinking: “If you understand those things that is the entire course really.” L90
  • Architecture’s goal is scalability, meaning all three roles win (users, customers, developers). You achieve or lose it through the four pillars. L90
  • Bad design example: packaging by infrastructure (routes/, controllers/). Structure should “progressively move inwards”. L90
  • Coupling is the enemy of testing. Insert a contract between two clumps (one implements it, one relies on it) and repeat to isolate smaller clumps. L90
  • Framework patterns map to agnostic patterns (Redux store, single-file components → DTO, controller, presenter, observer, gateway, view model), which derive from the six RDD stereotypes. L90
  • Read path: gateway/API client → cache → observer/coordinator → presenter → view model → component, bound via useEffect or MobX. L90
  • Write path: component → controller (use cases/command handlers) → domain object (e.g. RegistrationForm) → repository → gateway. Any state-changing command should pass through a domain object first. L90
  • Component state (ephemeral, useState) is separate from app state (the cache). L90
  • Strategy: small and medium frontends start with E2E tests. Carve out the pure middle (the high-value unit test zone) only when complexity justifies it. L90

Best Q&A exchanges

Q: What’s the goal of frontend architecture? Students offered easy to change, many devs on one codebase, easy to navigate. Khalil abstracted all of them into scalability: all three roles winning, via the four pillars. L90
Q: Don’t React Query or Apollo abstract all this? They handle fetching, caching and hooks. At responsibility-first you see their doings and knowings, map them to stereotypes, and either vet the tool or compose the missing responsibilities yourself. L90
Q: Is it OK to share models between frontend and backend? Yes. Share value objects and their validation from a shared package. Frontend-only domain objects like RegistrationForm still exist. L90

1-on-1 Part 1: Category Theory, Frontend Architecture, Metaphysics & RDD L94

Undated. Student Lucas is building a canvas drawing app like Excalidraw or Figma, and his canvas object is being passed to and changed by everything. Khalil goes down to first principles, then runs upfront FA²STR on a “zoom in/out” feature.

Top insights

  • Diagnosis: clarity and overwhelm. “Camera service” is too big and vague a building block; “everyone calls everything a service”. L94
  • Phases: code-first → pattern-first → first principles. The gateway to first principles is RDD, where responsibilities (doing/knowing) are the smallest building blocks (an idea from Scott Bellware). L94
  • Metaphysics chain: essence → actor/role/goal → purpose → form. For drinking coffee, the mug’s hole is essential and “printable” is not. A stone is a toy, a weapon or a tool depending on who uses it. L94
  • Essence of software: computing solves problems through sequence, selection and iteration. A problem = state A → state B. Transition = behavior, event = the fact it happened, data = initial state + events, namespacing = abstraction for understanding. L94
  • “The correct architecture is the event-based one”, because it works with the grain of reality. Event sourcing and CQRS strip away everything but that essence. L94
  • Pick the guess point first. Zoom is most likely level 3 (application), since it involves coordination and control. L94
  • Stereotypes assigned: Canvas = interfacer; MouseEvent = information holder; app events observer = coordinator; CameraController = controller (delegates the change); Camera = structurer (≈ aggregate); the math = likely service provider. L94
  • Control center = coordinator + controller. Take it back from React and push React to infrastructure, and ~90% of core use cases become testable without starting React. L94
  • Match rigor to product stage. Ship fast in React until the value is validated, then play defense. “There’s no right tests always.” L94
  • Frontend state: delegated (watch specific objects) or centralized (a Redux-like application data model). Both have trade-offs. L94

Best Q&A exchanges

Q: Isn’t abstraction essential to computing, since even reading voltage as binary is abstraction? “Good point.” Abstraction is the first of the three metaphysical essentials, and understanding may be the essence of everything. L94
Q: Does the controller make the change itself? Usually not. It orchestrates, and a stateful updater (a “camera repo”, like a repo saving a post) performs it. L94
