Architecture & Code Structure

An architect makes the smart decisions at the start of a project. Most of those decisions come from knowing one stereotypical architecture (read/write paths, events, layers, the dependency rule) and from picking tools by responsibility and non-functional need. Code is structured feature-first: modules/ for the customer, shared/ for the developer, tests mirroring features. A modular monolith wired by an event bus is the default starting point. L32 L92 L71

Layer mechanics (dependency inversion, repositories, fakes, the clock contract) live in Horizontal Decoupling. The composition root lives in Composition. This section covers the architecture-level view and code structure.

What an Architect Does & the Stereotypical Architecture L32 L88

Architect

“What is an architect really? It's about making the decisions at the start of a project that are going to be really smart to make.” The skill comes from experience plus education. Education means knowing the foundational styles and patterns, summarised as the stereotypical architecture, plus a working knowledge of platforms and tools. L32

The laws of the stereotypical architecture

The same architecture shows up on frontend, backend and desktop. Hexagonal, onion, ports & adapters and even event-driven are all “one stereotypical architecture.” L32 L88

1 · CQS: read path + write path

“There has to be a read path and a write path.” Commands change the system; queries read it. L32 Khalil files CQS under vertical slicing. L91

2 · Event-based

“We could scale features horizontally because we could just temporally decouple features.” See Temporal Decoupling. L32

3 · Layers of concerns

Horizontal decoupling. Put responsibilities in the correct abstractions, assign those abstractions to layers, and let abstractions talk only to the appropriate ones. Layers: domain → application → adapter → infrastructure. L32 L88

4 · Dependency rule

“An abstraction inside of the application layer is not necessarily supposed to know about directly an infrastructure concern. That's called the dependency rule.” L32

Domain layer concerns (4): data, rules, relationships between data, processes. The domain model is “anything tasked with representing your data, your rules, your processes and your relationships.” L88 L84 Khalil pictures it as “building this little world and just connecting to it using infrastructure.” L88

“Once you're aware of the stereotypical architecture and the layers and the concerns within those layers, you can't unsee it.”L88

Once you know it, you always know when a concern is missing and where to encapsulate it. L88 Many devs struggle to piece an architecture together because they don't know what the stereotypical concerns do or where they belong. Khalil's example: where does React Query go? L93

Picking tools: it all comes down to responsibilities

A large part of architecture is “choosing the best tool for the non-functional task that you need to accomplish.” You can only choose from tools you know, so keep learning platforms (static sites, SSG, serverless, Docker, Kubernetes, an event bus, MongoDB). For each one, learn both its functional and its non-functional reasons. L32

  2. List functional requirements and NFRs — the NFR (how the system does a slice) is “where the real complexity lies.” L92

How to become a better architect (Khalil's path) L32
  1. Climb the phases of craftship and note the styles, patterns and tools you meet: 3/4-tier, hexagonal, event-based.
  2. Learn the stereotypical architecture.
  3. Learn object design (responsibility-first) to glue the pieces together.
  4. Use guess points and systems thinking to decompose problems and route them into the right systems.
  5. Try new tools on your own time (Docker, Kubernetes, an event bus, MongoDB). Learn what each is and why it helps non-functionally, then plug things together.

Why layers exist at all: places to test

“Everything we're doing is a guess.” Layers (domain, application…) are “giving you different places at which you can write tests that are going to have different impacts.” Application-layer tests exercise core functionality without starting React, a database or a web server, which is “incredibly valuable.” L28

Ratio: roughly 1 E2E test : ~10 high-value unit tests. The unit tests give ~80% of the confidence and take ~80% of the work. L28 See also ~10–12 application-level scenarios per acceptance test. L82

Anti-pattern: patterns without the why

Khalil learned DDD before he knew how to write tests, and calls it a mistake. Don't “chuck yourself into it and just start using patterns and then get stuck on the patterns because you don't even really know why you're using the patterns.” L28

Structuring a Codebase: Features First L35 L29 L92 L93

Judge structure through the abstraction prism, which Khalil calls “the key thing here.” Structure exists to serve the key developer use cases: discover features, work on them, test, extend and remove them. L35 Khalil revised his earlier pages/components advice. Organise by feature, the level where all three roles collaborate: “I think this is where stuff should begin becoming code… from this level of the feature.” L92

North star 1 · Key developer use cases

Discover, understand, test, add, change, execute and remove features. L29 L35

North star 2 · Customers decide

Drive code outside-in from the customer boundary, starting with E2E tests. Building a component library or tiny functions first is “fundamentally flawed.” L92

North star 3 · Discoverability & understanding

Open the codebase and see “in a second or two” how to do the use case. This is the hardest part. L92

Before — package by infrastructure: features invisible, cohesion accidental

“I hate packaged by infrastructure.” L88 Two folders for one concept (fake and testing utils) is a cohesion smell. Merge them. L84

After — modules for the customer, shared for the developer, tests mirror features

“Use cases define features, which define modules, which define sub-modules.” Khalil: “that's precisely it.” L92 src/modules/<capability>/<feature>, mirrored in tests/ with acceptance tests per feature. L29

modules/: for the customer

Essential complexity: code related to the problem itself. “It's almost like this modules folder is for the customer. And this folder is like for the developer.” L92

shared/ (shared/core/): for the developer

Accidental complexity and cross-cutting concerns, “what is required”: use-case and entity base classes, a RESTful API driver. L92 In FeedBook: core utilities plus shared domain descriptions. L71

Two kinds of slice

(1) The module: capability or bounded context, the thick cut. (2) The operation: an API call, a thin input→output cut. Features/workflows sit in between. Cohesion decides how thick to cut. L93

Rules
  • For every new abstraction ask: essential (modules/) or accidental (shared/)? L92
  • Keep siblings at the same level of cohesion. Test candidate names: is posts/ a peer of users/, or is forum/ the module and posting the feature? L92
  • “If you can't see your features from the folder structure alone, there's a good chance maintainability is under pressure.” L93
  • Folders ≠ layers. Layers are theoretical and don't need to map to folders. L84 The folder tree follows features/modules/slices. The network of objects inside a module follows the stereotypical architecture. L92
  • Rely on knowledge in the world: src/ and tests/ need no explanation. Call out uncommon folders like packages/ in the README. L92

The README test: 1–2 seconds to a developer use case

  1. README — has a table of contents such as “how to add a feature,” “how to test features,” and says “go to the tests.” L92 L93
  2. Tests by capability — the tests folder is broken down by capability. L93
  3. A feature file per feature — stories → acceptance criteria / scenarios with concrete examples. L93
  4. Then into code — the matching src/modules/… folder. L93
“It's about language. And it's about cohesion and it's about design and it's not precise… It requires constant scrutiny and philosophizing.”L92

This is covered in the Best Practice First phase. Drive structure decisions through the theoretical and the physical, not through anxiety. L35 L91

Understanding Large Codebases via Features L29 L92

A developer's one main task is to keep delivering user and customer benefit, and “the work that you need to do is entirely on features.” So “if we were to maneuver into the code base, you are looking for features.” Hunting features is the 80/20 of understanding a codebase. L29

Feature

“Features are not just specific operations, API calls. Features are user stories or more general.” In the prism: who → why → what (capabilities) are theoretical; features are the “how.” Modules map to capabilities. L29

Feature tracing: when there are no acceptance tests

  1. Find the common features — ask people, read tickets, ask which features are most used, use the frontend app. L29
  2. Trace each one into the code — “try to trace to find out how that feature is realized in the code base.” L29
  3. Infer the original mental model — the tracing shows how the original developers thought. L29
  4. Make features explicit — add a layer of tests that represent features specifically. L29 In a messy codebase, “stop the bleeding” first with E2E tests that wrap the whole thing (the tailor's pins), before any pattern-first refactor. L92
Live demo: “add create post” to DDD Forum L92

Walking in as a newcomer: the README “is not helping.” Path taken: packages/ → backend/ → tests/ (test-first) → acceptance/ (“what is that?”) → users/. Should posts/ go next to users/? Maybe forum/ is the module and posting the feature. “It's philosophizing every, every step of the way through.” The process: walk every developer use case from the README and make each one clearer.

When interfaces make navigation painful: use feature folders, cohesive naming, and consistent layer rules so use cases predictably reference interfaces. See Vertical Slicing. L84

An agent dropped into a modules/<capability>/<feature> tree with a README “how to add a feature” reaches the right file in one or two hops, and the mirrored feature tests tell it when it's done. Modules as Mini-Applications: The Application Interface L92 L88

A student suggested that each module could be its own application with well-defined interface points. Khalil connected this to the application interface pattern: express the whole app as one API that says “everything that your app can do.” The app implements it (pure), and delivery mechanisms such as a web server use it. L92 L88 It applies the composition essential: “one big object” composing all the use cases. L88

  • Payoff for tests: incoming-adapter tests replace the app with a fake. They check only that endpoints call the correct use case with the correct parameters. L88 L92 Code in Value-First Test Strategies.
  • Payoff for design: without it, “you end up building your app within your framework” (a student's point, which Khalil endorsed). L88
  • Is jobs a feature, a module or a bounded context? Student: “It's both a module and the feature.” Khalil: “It's tricky stuff.” L92

Modular Monolith vs Microservices L84 L71

A tech lead planned to rewrite an MVP as microservices with two backend devs. Khalil's framing: that is a theoretical architecture guess made before the problem is understood, and it “has exploded into more guesses for you to make”: observability and telemetry across deployable units, messaging infrastructure, deployment. L84

Justify potential negative value

Every architectural complication must be “solidly justified” against the negative value it can introduce. You may not even be aware of the guesses you're forcing on yourself. L84

Fewer components → fewer guesses

“The least amount of components you have to manage means the least amount of guesses you have to make.” That's why serverless is popular: you get to focus on the guesses you want to make. L84

Extensibility from first principles

Maintainability and extensibility come from vertical slicing plus horizontal decoupling, not from deployment topology. Reading: Vaughn Vernon's Strategic Monoliths and Microservices. L84

Modular monolith ≠ single process

“Modular monolith does not mean modular process. This is just how you organize your code.” Several modules live in one project, and at bootstrap you choose which ones share a process. “Usually a better place to start than microservices.” L71

How to organise it

  • Subdomain classification drives folders: core = build it; generic = import a library; supporting = build it anyway, reluctantly. By the architecture step “we've done the majority of the hard work.” L71 Details in the FeedBook architecture guess point.
  • External services are collaborators: wrap the minimum integration code (Stripe, PayPal, mail) in a service. L84 Don't build generic subdomains such as auth or your own SMTP server. L88
  • Event bus as the backbone: everyone registers and subscribes to events. Deploying everything in one process is the easiest start. Students proposed SOA without a bus, or WebSockets; the course goes event-driven. “At the end of the day, we just need coordinators.” L71
  • Microservices in the course: not covered in depth. The course covers the foundations: temporal decoupling, vertical slicing, horizontal decoupling, deployment. L84
Anti-pattern: the makePurchase transaction script L88

Get cart items → check inventory → bill the card → update inventory → send email, all in one call. A crash between billing and the inventory update leaves an invalid state. Khalil did this on the solidbook site and suffered, with serverless cold starts cutting requests. Instead, model subdomains (e-commerce, orders, billing, emails, inventory), each its own state machine, talking via events.

AI-era lens · Copilot

An agent can scaffold ten microservices in an afternoon, but the operational guesses (observability, messaging, deploys, partial failure) don't shrink with it. Default to a modular monolith with explicit module boundaries and event contracts. Split processes only when an NFR justifies the extra guesses.

Monorepo: Frontend, Backend, Shared L35 L82 L81 L28

In Best Practice First the project is a monolith inside a monorepo: frontend and backend in one project, sharing code. L35 The layout is frontend/, backend/, shared/. shared/ holds the acceptance tests (a shared executable spec) and later the shared models and DTOs, which are covered in Pattern First. L82 Kirill's exploration kept it minimal: a shared package via NPM workspaces for DTOs and even domain objects. L81 Refactoring to a monorepo lets you share DTOs and value objects between frontend and backend. L28

  • Each side gets its own MVC. Extract service/application/domain layers on both sides, and use controllers and presenters on non-trivial frontends. What gets shared is the acceptance tests, and later models and DTOs. L82
  • In DDD Forum's frontend, UserRepo does the work, “synonymous to a use case” on the backend: it takes the registration form, creates a DTO, sends it, and caches the result. L81
  • Hosting setups vary (Next.js/SSR, a backend-served frontend, Netlify + Heroku). That decision belongs to the architecture guess point. L82 Monolith vs monorepo is part of the walking skeleton. L93 Frontend specifics: Frontend Architecture.
