12 Essentials II: Physical

The seven physical essentials turn a clear “what” into running, verified, shipped code. Slice work by features, split each slice into layers, push time-based requirements into events, compose the parts in one place, put a boundary around what you verify, deploy a walking skeleton first, and gate everything with a deployment pipeline. Vertical Slicing L16 L93

Definition

Decomposing work into manageable chunks, meaning vertical slices of functionality. You chunk modules, features and operations into slices so that features are first-class citizens in the code structure and in how you approach the work. L16

Feature

Valuable to the customer. Described by a user story that takes someone through an experience from A to B, involving many API calls. Example: “register and sign up for a premium package on a membership website.” L16

Operation

A lower-level slice: a command (changes the system, e.g. createUser) or a query (reads it, e.g. getProfileDetails). In practice an API call, a thin input→output slice. A sequence of operations builds a feature. L16 L93

Module / capability

The thick slice: a high-level module, bounded context or capability (profile management, friending, settings). Features/workflows sit between modules and operations. Cohesion decides how thick to cut. L93

Why

  • Design = discoverability and understanding. It must be easy to find what you need. L16
  • It matches reality: developers work against features. The key developer use cases are to discover, understand, add, change, remove, test and debug features. L16
  • Your mental model shows up in the code. Other developers read it back out. Thinking in “tiny scripts” produces tiny scripts. L16
  • The most valuable thing to test is the feature, not createUser/editUser in isolation. Features come out of the theoretical guess points, and acceptance tests are written at the physical ones. L16

How

  1. Start from features — derived from customer needs and user stories, not from endpoints. L16 L82
  2. Cut modules by capability — “feel into” how thick to cut, judged by discoverability and understanding. Vaughn Vernon’s domains → bounded contexts → sub-bounded contexts is an optional deeper cut. L93
  3. Make features visible in folders and tests — a feature can be a folder, a file, or just a feature file in tests. Ideal entry path: README says “go to the tests” → tests by capability → a feature file per feature → stories → scenarios with concrete examples → code. L93
  4. Navigate like a table of contents — source → modules → domain → feature → operation → the component misbehaving. This works when combined with horizontal layers (the grid below). L18
  5. Self-check — Can you see the features in your code base? Could someone else find them? How hard would it be? L16
Before — package by infrastructure: one feature is smeared across five folders
After — package by feature: the folder tree reads like the product
Anti-patterns
  • Packaging by infrastructure: folders by technical type hurt design, discoverability and understanding. L16 Khalil: “I hate packaged by infrastructure.” L88
  • Transaction-script thinking: treating work as “just adding code” to tiny scripts. L16
  • Starting from React components: “not the worst thing,” but it doesn’t match the key use case of working against features. L16
  • Thinking in endpoints instead of features, typical of code-first. L82
  • Testing operations as if they were the most valuable unit. L16
When interfaces make navigation painful

Khalil’s three-part answer: (1) slice features into feature folders, (2) use cohesive folder structure and naming (a name also says what something is not), (3) follow the layered-architecture rules so you know what to expect, since use cases always reference interfaces. L84

“If you can't see your features from the folder structure alone there's a good chance maintainability is under pressure.”L16 L93
“It is the internal representations that we have in our minds, the mental models that we're working off of, that's what is going to show up in our code.”L16

Roadmap: the main vertical-slicing work happens in Best Practice First (feature slicing). Pattern First adds read/write path separation and read/write models. L16 Deeper structure in Architecture & Code Structure; features come from the theoretical essentials.

Agents follow the structure they find. In a package-by-infrastructure repo, one feature change sprawls across controllers/, services/ and models/. Feature folders plus one .feature file per feature give the agent one place to work and one oracle to check against.

Horizontal Decoupling L17 L84 L88

Definition: two parts
  1. Awareness: know the well-known layers of abstraction, their directionality and stereotypes, so every line of code goes into the right abstraction instead of “no abstractions and just writing code.”
  2. Actual decoupling: strategically decouple those layers with dependency inversion (contracts), so you can isolate and put a boundary around what you want to verify.

It breaks down what happens inside an operation (a vertical slice) into categories of work, called concerns. L17 L93

Why

  • Locality: if the DB connection breaks, DB code lives in one known place. Less duplication: duplication appears when nobody knows where things belong, and the code “turns into mush.” L17
  • Testing options. Application and domain hold the edge cases, business rules, validation and policies, which is the most valuable code to test. Without decoupling you can only reach it by starting the whole app end to end, which means slow tests and slow pipelines. L17
  • Black-box testing only gives result verification. Edge cases such as “deactivate without delete, then rejoin → welcome back” become nearly impossible to cover through the black box. L84
  • Fast CI. Decoupling lets fast tests run in CI instead of E2E-only suites. L93
Two problems of the naive backend, and their fixes L88
  1. E2E tests don’t scale. Every feature test goes through the whole app to the DB, and setting up DB state (fixtures) each time is slow and complex. Fix: dependency inversion. Describe persistence (and external services like a PaymentService) as a contract. Core code “uses / relies on” it; the real DB, Stripe or a fake in-memory version “is a / plays the role of” it. “It's always way faster and easier to manipulate something in memory rather than in disk.”
  2. Controller, application logic and business logic are fused, so even with a fake DB you still go through Express. Fix: an application interface. All use cases are composed into one pure object; the app implements it and the web server uses it (see Composition).

A third problem is lack of encapsulation: pulling validation into a random function in another file keeps data and behavior apart. L88

Before — fat route: HTTP, rule and SQL in one place, testable only end to end

This is the “anemic domain model” shape. There’s no place where the rules live, and no horizontal decoupling. L84 Almost everybody starts here, and it “looks kind of elegant.” L88

After — slim controller → use case → repository contract; fakes make the core testable

Keep the fake honest with a shared contract test L81.

How: rules

  • Know the layers: infrastructure → adapter → application → domain. MVC, Clean, Onion, Ports & Adapters/Hexagonal are all related (“it is all related”). They are one stereotypical architecture you “can't unsee” once you know it. L17 L88
  • Stereotype each abstraction. A React component presents, accepts input and passes it off (interfacing), so it belongs to infrastructure and never touches a database. L17
  • Classify code by what it touches, not where it comes from. An npm library that just returns a string is core. Express is infrastructure because it opens a port. L84
  • Use cases depend on interfaces (roles), and concretions (actors) are injected via the constructor. “The repository is the adapter… it is a role to be played.” L84 L88
  • Start with an interface, and move to an abstract class only after the rule of three shows a real need to share implementation. L84
  • Keep controllers slim: pull data out of the request and pass it to a service layer. The evolution is view → controller → DB, then carve out a service layer (four-tier), then a pure application + domain core behind contracts. L82
  • Know the rules well enough to break them knowingly, and to marshal “mush” back into testable code later. L17
Quiz from the live session

Where does await this.repo.save(post) belong? Answer: in the application service / use case (application layer, high-level persistence logic), not in a controller. L93

Decoupling from time: the clock contract

new Date() and Math.random() are infrastructure because they touch the system clock and random generator. The domain model must be pure: no system time, no Math.random, no setTimeout. Otherwise tests have to wait (e.g. 30 s for a traffic light). Put a clock contract in between. Khalil notes that passing the date value straight into the constructor is “not great.” L84 L88

Before — hidden dependency on the system clock
After — time is a role; tests control and travel it
Anti-patterns
  • Responsibilities living in the wrong place, which leads to duplication, confusion and “mush.” L17
  • All logic in the Express controller (anemic domain model): only black-box testable. L84
  • Injecting a concrete DB/ORM into the use case, which makes it infra-dependent and slow to test. L84
  • A React component that knows about a database. L17
  • this.repo.save(...) in a controller. L93
  • Writing code “until the thing works” with no thought to where things belong. “You haven't been bit yet.” L93
“What we want here is some order, some structure and a clear place for abstractions to go.”L17
“Ultimately, what we need is more testing options… The skill that is going to give you more testing options is the skill of dependency inversion.”L17
“It's not about where it comes from it's about what it touches.”L84

Roadmap: MVC in Code First → layered architecture plus 4-tier non-flaky E2E tests in Best Practice First → core vs infrastructure and ports & adapters in Pattern First → stereotypical architecture in Responsibility First. L17 More in Architecture and Abstraction & RDD.

Temporal Decoupling L18 L93

Definition

Decoupling functionality with events, instead of slotting new operations into existing ones. When a vertical slice completes, it publishes an event (e.g. OrderPlaced). Event handlers listen and invoke new vertical slices, sometimes in entirely different systems. L18

Coupling is “the tightness or the interconnectedness of modules or lines of code.” L18

Why

  • Requirements are temporal. They arrive as “after this do that,” “before this happens,” “only when this happens, if this is already true,” or “if in production/dev.” These are policies. L18 “The nature of reality is… temporal… It's event based.” L93
  • Appending breaks things. Steps block each other. If the notification service fails, the important steps after it never run and the system is left undefined. To verify one follow-up you must run everything. L18
  • Speed. If Amazon billed, emailed, updated inventory, created fulfillment and logged analytics inside “place order,” requests would be too slow, and “probably no one would be using Amazon.” L18
  • All-or-nothing. Never leave “billed the customer but inventory not updated.” Khalil did exactly that with a makePurchase transaction script on the solidbook site, and serverless cold starts cut requests midway. L88
  • Hard to retrofit. Temporal coupling is “only solvable… from the very start,” so design event-based architecture from day one. L93
Before — one request awaits every follow-up, and one failure strands the rest
After — the slice ends at “order placed”; handlers start new slices

Added by Copilot An in-process bus loses events on a crash. Production backends need persistence and exactly-once/outbox-style delivery, which Khalil lists as backend concerns of the coordinator L93.

How

  1. Hear the time words — treat “after / before / when / only if” as signals for events and policies. L18
  2. End the slice at its own state change — the Gherkin “then” became “an order should have been placed” rather than “he is billed / emailed,” because that work must be temporally decoupled. L82
  3. Publish, then react — handlers call follow-up slices. Start simply with a coordinator (the object stereotype whose one job is to take in events and let other parts know; basically event listeners), and make it robust later. L93
  4. Keep flow unidirectional — event → bus → command → command handler, cycling one way, as Redux does. L93
  5. Model success, then failure — for each decoupled step, ask what happens if it fails and design compensating events (billing fails → email, wait, cancel after 3 days, release inventory). L18 L88
  6. Use it to find aggregate boundaries — if you can’t find the boundary, “you're probably trying to do too much in one command.” L88
Frontend vs backend

Front ends likely already have this: every front-end architecture needs reactivity, and Redux does it. The backend holds more high-level policy, so decoupling operations and thinking through success/failure paths matters more there. L18

Anti-patterns
  • Continually appending functionality after a core action in the same operation. Khalil’s own “after job posted” code was “a terrible way to add functionality that comes afterwards.” L18
  • Sequential blocking calls where one failure prevents other important work. L18 L93
  • A mail service as a direct dependency of CreateUser. Khalil corrects his own diagram for this. L20
Terminology note

The course describes idempotency as “anytime we do anything in our system, it's going to keep the system in a consistent state” L18, and uses it for “either this whole thing works or none of it works” L88. Added by Copilot Standard usage: idempotent means repeating an operation has the same effect as doing it once, which is vital for retried handlers. All-or-nothing is atomicity.

“The reality is that requirements are temporal.”L18
“When you do place order, what's happening is Amazon is dispatching an event.”L18

Khalil’s own caveat: “This topic is even one that I am not particularly an expert in. I just know a lot from the experts.” L18 Roadmap: unit of work and event-based backend architecture in Pattern First; custom builds in Responsibility First. L18 Events also drive event storming and process modelling.

Generated code appends side effects as sequential awaits by default and rarely handles the failure path. Spotting “after / when / if” requirements and asking for an event, its handlers and a compensating event is a human design decision.

Composition L19 L93

Definition

Consciously, not unconsciously, creating a network of collaborating abstractions. You pass in each part’s required dependencies, and their dependencies, like Russian dolls. Done well, the app is configurable from one location and dynamic runtime behavior is easy. It is “more than just a passing design principle” like “prefer composition over inheritance.” L19 L93

Truth 1: software is made of many parts

Code-first developers wire parts unconsciously: copy from docs, Stack Overflow or ChatGPT, then plug things together until it works. The result is cyclical dependencies and code that is hard to understand, maintain and, most critically, test. L19

Truth 2: software runs in many environments

Dev, test, CI, staging, production. Some things toggle per environment (e.g. Redux dev tools on in dev). Handling this needs polymorphism, “the ability for your code to take on different shapes.” L19

How

  1. Decouple first — composition depends on horizontal decoupling. Without concerns in buckets there’s “nothing to swap”; it’s “jiggly puff type code.” L93
  2. Respect directionality — outer-layer concerns rely on inner-layer ones. L19
  3. Trace the graph — follow every dependency all the way up to the web server. “It forces you to really have a tight awareness of how you're linking up your code base.” L19
  4. Encapsulate wiring in a composition root — one object does all linking and holds the environment checks. Stop importing things “willy nilly” in Express controllers, which hides the object collaborations: “Apps are all made from objects that talk to each other.” L19 L82
  5. Grow deliberately — start with a composition root (poor man’s DI). Switch to a DI container only when it gets messy, per Mark Seemann’s effort-vs-messiness graph in Dependency Injection. L93
Before — environment checks and dependencies grabbed inline
After — dependencies passed in; environment decided once

Where it pays off

  • Testing: swap dependencies at the application guess point (and the system and incoming-adapter guess points). You can test an entire front-end feature without starting React or setting up Redux. L19
  • Application interface: clumping all use cases into “one big object” is an instance of composition. Incoming-adapter tests then only check that endpoints call the correct use cases with the correct parameters, without running them. Without it, as a student put it, “you end up building your app within your framework.” L88
  • Deployment pipelines: code must be composable up front to run in many environments. “We 1000% will have to use it.” L19
  • Reproducible dev infra: encapsulate provisioning in the code base (Docker instead of a local DB). L82 L81
  • Plugin architectures: VS Code extensions and themes, new weapons in a game, audio nodes in a DAW. Aim for an app that is “polymorphic in general.” L19 L93
Code review from the live session: connections

A student built each module’s repository per request (async UserRepository.build()) to avoid long-lived DB connections. The consensus: per-request connections cost handshakes and suffer serverless cold starts, and callers might forget to await the async build. Instead, create a DbConnection abstraction once at bootstrap and inject it into thin repositories through the composition root. L93

Anti-patterns
  • Copy-paste-plug-until-it-works wiring; treating design as only folder structure. L19
  • Cyclical dependencies from unconscious linking. L19
  • Environment checks littered through the code base. L19 L93
  • Front-end code that can only be tested E2E because abstractions aren’t known or placed. L19
“The way in which we link together our dependencies is incredibly important.”L19
“It's about creating dynamic behavior and that we need to link things together almost like a Russian doll.”L19

Roadmap: mainly Best Practice First (refactoring code-first work with composition), used heavily in Pattern First; DI containers in Pattern/Responsibility First. L19 L93

AI-era lens · Copilot

Generated code is the new “paste from Stack Overflow”: inline new, hidden imports, scattered env checks. Insist on constructor injection and a single composition root so the dependency graph stays auditable and every piece stays swappable for fast tests.

Subject/System Verification L20 L84

Definition

Using tests to place a boundary around the thing you want to verify, so you can tell whether it helps achieve a goal. It treats the application as nested input/output systems, decomposed by vertical slices and horizontal layers, so you can isolate specific parts. L20 Khalil prefers the term subject. L88

Why

  • “The reason why we write tests is because everything we're doing is a guess.” This is the feedback loop made physical. L20
  • Developers struggle with testing because it’s treated as an afterthought instead of something foundational. Learning it “means learning 18 other things at the same time.” L20 L93
  • If you can’t draw the boundary you need, that tells you to apply more horizontal decoupling, vertical slicing or composition. “It all builds on each other.” L93

Three types of verification

1 · Result

Inputs → outputs; the environment is unchanged. Simplest, and the only kind possible through a black-box E2E test. L20 L84

2 · State

Act on a loaded model with no direct output, then reach into its state. Found by programming by wishful thinking: write the assertion with the API you wish existed. L20 L84

3 · Communication

Verify the subject talks properly to its dependencies: indirect inputs (repo fetch) and indirect outputs (repo save). Hardest, but it “is going to lead to the tests that are the most valuable.” L20 L84

Result and state verification are often combined in the same test, which is “completely fine.” L20 Full technique coverage (spies, builders, AAA backwards) is in Testing L53.

How to choose the boundary

  1. Name the guess — the test type depends on the guess you are validating. Example: do API calls route to the right use cases and do contracts still hold? That needs a boundary from the outside world to the use-case entry. L93
  2. Pick the layer — for API stability across mobile, web and desktop clients, test at the incoming adapter. For “a job posting cannot be edited after 48 hours live,” test in the domain layer. L20
  3. Widen for side effects — to verify a welcome email after createUser (temporally decoupled), the subject must include the event infrastructure for UserCreated, plus a spy on the mail service. L20
  4. Prioritise features — the most valuable thing to test is what’s most valuable to the customer. L20
  5. Make fast tests valuable — “We want the tests that run really fast to be tests that are also incredibly valuable”: high-value unit tests in the pipeline’s fast stage. L20
“We're only testing our mocks” → contract tests

That feeling means the fake and prod implementations lack test parity. Run one integration spec across all implementations of the interface: “You're testing the contract, not the implementation.” Use library mocks only for trivial stubs (a logger); for stateful dependencies, use fakes covered by contract tests. L81

Three test categories L82
  • Acceptance: does this do what the customer wants?
  • Unit: does this do what I, as a developer, think it should? Domain and application logic; about 80% of the work.
  • Infrastructure: does this infrastructure do what I want (start/stop DB, connect, start/stop web server)?
Anti-patterns
  • Testing as an afterthought. L20
  • Relying only on E2E/black-box tests for rule-heavy features. L84
  • Getting lost in mock vs stub vs fake taxonomy; just say “test double.” L84
  • A fake repo and a prod repo tested separately with no shared contract. L81
“It's us placing a boundary around the thing we want to verify to be able to tell if it's going to help us achieve a goal.”L20

Roadmap: manual testing in Code First → test infrastructure and acceptance tests in Best Practice First → patterns for the most valuable tests in Pattern First → outside-in, test-driven work with FA²STR in Value First, “perhaps one of the most valuable things I can teach you in this course.” L20

When agents write the code, choosing the boundary and the verification type is your main lever. State and communication checks catch code that returns the right value but never saves or emits. Contract tests stop an agent-written fake from quietly drifting from prod.

Walking Skeleton L24 L81

Definition

“Build the smallest slice of useful functionality and deploy it as quickly as possible,” verified by an automated end-to-end test in the most production-like environment possible. L24 “It's exactly the same thing as a tracer bullet” (The Pragmatic Programmer): the most bare-bones valuable thing, shipped in front of someone. L81 It is “a minimal slice of functionality through all of the main architectural components.” L82

How

  1. Get very clear on the theoretical — the problem and the solution. L24
  2. Get clear on architectural components — patterns and how they play together. L24
  3. Draw a broad-stroke architecture diagram. L24 L93
  4. Build it and test it end to end — functionality that cuts across all main components, UI → DB. L24 L93
  5. Figure out how to deploy it — with a minimal pipeline, because “working software” means software void of bugs, so even the skeleton needs a guard phase. L24 L81
Decisions the skeleton forces early
  • Monolith vs monorepo, source control, CI, deployment pipeline, test infrastructure, scripting. L24 L93
  • A reproducible setup so others can pull, run and test; Docker to encapsulate infrastructure. L24 L81
  • Developer ergonomics (folder structure, README): “things are admittedly never going to be easier” than at the start. L24

Where it sits

  • Guess points: architecture guess point → (physical) E2E test across everything → deployment & delivery → execution guess point. The question at the end: “Can users even use this thing? Will this even work? Does it deploy?” After users use it, check KPIs, which loop back into what to build next. L24 L81
  • After the skeleton you’ve “made a pretty big mess.” The rest of Best Practice First improves the design so Pattern First work is effective. L81 Next come proper scripts, clean runs across environments, working composition, a confirmed test strategy, and tests embedded in the pipeline. L25
  • Existing messy projects: kick off a new feature with a skeleton to pull the codebase toward structure. L24 For existing features, pin behavior with characterization tests first; don’t rewrite from scratch. L81
  • It is architectural and strategic at once: it sets up design and the testing foundation together. L82 It is step one of the ideal developer workflow’s physical side.
Anti-patterns
  • Building components for weeks or months without DB/web server, deploying last. L24 L82
  • Assuming you can predict the snags of the physical realm: version conflicts, outdated tools, containerization issues. L24
  • Working in front-end or back-end silos without an end-to-end slice. L81
“We want to get the most bare bones version of something that is valuable to somebody out shipped in front of them.”L81
“Make sure that we can actually score this thing through the goalpost.”L82

Deployment & Delivery L25 L93

Definition

Make sure the tests you write actually gate what ships, so you never ship negative value: “bugs, defects, anything that is going to take the users out of benefit.” The tool is a deployment pipeline, a constraint (from Don Norman’s The Design of Everyday Things, “something that limits you from all the possible sets of things you can do”) that enforces a single path to production and a minimum quality standard. L25 The ideas come from the Continuous Delivery / DevOps movements: “I'm not the brainiac that invented this.” L93

The phases

  1. Commit phase — lint (code looks standard), build, run tests. Ideally these are high-value unit tests, which test features purely and fast, not just front-end component tests. Package the artifact. Passing unit tests should give ~80–90% confidence, which is only possible with a pure, decoupled core. L25 L81 L82
  2. Release candidate — a deployable artifact (zip, Docker image…), the version that becomes production if later stages pass. L82
  3. Acceptance phase — set up infrastructure mirroring production (staging) and run E2E tests as acceptance tests. They test the same things as high-value unit tests, but through the whole system, as a user would. Infrastructure tests can run before or after: “doesn't really matter.” L25 L82
  4. Deploy — manual or automated. L25

Rules

  • One path to production: make it “virtually impossible for someone to ship negative value.” L25
  • Start minimal, then add phases (security, performance). Pipeline speed can keep improving; some people’s whole job is that “runway before code gets out to users.” L25 L93
  • Fast things pre-commit, slow things in CI. E2E in a pre-commit hook was “so painful… everyone would just turn it off.” If you can’t build a full pipeline, run some tests in one. L81
  • Know how you’ll deploy before building (a theoretical guess); work it out concretely during the walking skeleton. L25
  • Testing ROI pays off here. Manual walkthroughs are fine at first but slow everything down as features grow. L25 L93
Anti-patterns
  • Relying on manual testing/walkthroughs as feature count grows. L25
  • Only running front-end component unit tests instead of feature-level tests. L25
  • Local hooks (Husky) as the quality gate: “There's nothing stopping any developer from just turning that off locally.” L25 L81
  • Writing all tests as E2E acceptance tests, which are slow and need the full app, DB and server. L82
“The entire purpose of a deployment pipeline is to ensure that our code is up to a minimum standard of quality.”L25
“We make it very hard to ship negative value to our users.”L93

Test strategy per stage: Testing. Where it fits in the flow: Ideal Developer Workflow.

AI-era lens · Copilot

Agents, like people, skip local hooks, so a CI pipeline is the constraint that can’t be bypassed. Keep humans owning the pipeline design and the test boundaries it enforces; that’s where quality judgment lives.
