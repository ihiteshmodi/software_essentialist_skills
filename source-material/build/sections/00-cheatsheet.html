FA²STR: Six Steps, Input → Output L27 L52

  1. Find: problem statement → responsibilities (doing / knowing), concrete examples, and the starting guess point. At higher levels the output is role, why and capabilities, then features, stories, acceptance criteria and examples. L52 L27
  2. Architect: responsibilities + examples → the subject under test. At higher levels: patterns, components, the testing strategy and a broad-stroke architecture. L52
  3. Automate: SUT + examples → a test harness and scripts that also run in the pipeline. Success criteria are defined before any code. L52
  4. Specify: one example → a failing spec (red). At feature level this is the outer-loop acceptance test. L52
  5. Test: failing spec → passing code, written with AAA and made green by fake it or the obvious implementation. Commit. L52
  6. Refine: passing code → refactored code once duplication appears three times. Commit, then loop back to Specify. L52
Remember
  • Upfront design = Find + Architect + Automate. Emergent design = Specify + Test + Refine. L52 L87
  • It works at any level. Start anywhere and drill in with n loops. L86 →
  • Everything is a doing or a knowing. Most tests are one doing with many knowings. L52
  • More than about four collaborating pieces? Go to paper and run RDD. L52

Ideal Developer Workflow: Outer & Inner Loop L26 L87 L40

  1. Clarify the theoretical guesses (Find): vision → role → goal → capabilities → concrete examples. Non-negotiable. L26
  2. Broad-stroke architecture (Architect): patterns, components, testing strategy, and how tests plug into the pipeline. L26 L81
  3. Walking skeleton (Automate): a testable architecture, a tiny deployed slice and a pipeline. L26 L87
  4. Feature work, n loops (Specify/Test/Refine): outer-loop and inner-loop tests, then fill the remaining ~20% and ship. L26

Outer loop · customer

A failing E2E acceptance test at level 5, written in the user's language. One per feature, shared by every platform. Result verification only. L87

Inner loop · developer

A failing use-case test at level 3 for each scenario (one success, many failures). About 80% of the time goes here. Recurse into levels 2 and 1 as new concepts appear. L87

Close it out

Adapter tests (levels 4 and 6), then hook up the view, then deploy. Infrastructure tests come last. L81 L87

Numbers to remember E2E: the happy path plus one or two sad paths. Then about 12–20 parameterized high-value tests. Roughly 1 E2E test to ~10 high-value unit tests, and those unit tests give ~80% of the confidence. L81 L28

The workflow is the same for an MVP and a mature product. Only the time, the effort and the quality of your guesses change. L40 → · MVP →

Testing Rules of Thumb L31

Rules
  • AAA backwards: assert → act → arrange. Start with the most complex example and program by wishful thinking. “Vagueness does not compile.” L51 →
  • Commit on green, never on red, and say whether the commit is new functionality or a refactor. Flip the switch to prove the test can fail. L44 →
  • Red for the right reason: export a stub first, so the test fails on logic and not on a missing import. L45 L49
  • Fake it until duplication forces a change. Use the obvious implementation only when you're confident. L45 L47
  • Rule of three: refactor on the third repeat. Never add examples during a refactor, and keep each step a refactor XOR a transformation. L44 L49
  • TPP: nil → constant → scalars → single statement → conditionals → mutation. If you need a variable or a mutation, question your transformation. L60 →
  • One example per loop, one it / one expect. L47 L55
  • Name tests as responsibilities (a doing or a knowing, e.g. “knows that …”). Keep examples concrete, in it.each rows that hold the input and expected output together. L56 L59 →
  • 3 verification types: result, state, communication. Pick by guess point. State or communication checks at E2E are bad practice. L20 L53 L87
  • Hand-written fakes and spies implement the contract. Keep library mocks for trivial stubs such as a logger. L73 L81 →
  • Contract tests for every fake: run one spec against every implementation. “You're testing the contract, not the implementation.” L81 →
  • Builders for fixtures: a fixture is the initial state. Give well-known states names. L78 →
  • Comments say why, never what. L48
  • Choose the strategy by ROI. There's no perfect strategy, and E2E-only or unit-only always fails. L64 L87 →

Design & Architecture Rules of Thumb L32 L88

Rules
  • Stereotypical architecture: CQS read/write paths, event-based, layers of concerns, the dependency rule. It's the same on frontend, backend and desktop. L32 L87 →
  • Dependency rule: domain → application → adapter → infrastructure. Inner layers never know infrastructure directly, and use cases depend on contracts. L32 L84
  • Classify code by what it touches, not where it comes from. new Date() is infrastructure, so inject a Clock. L84 L88
  • Feature-first folders: modules/<capability>/<feature> for the customer, shared/ for the developer, and tests/ mirroring the features. L92 L29 →
  • Composition root: one place wires dependencies and holds the environment checks. Move to a DI container only when that gets messy. L19 L93 →
  • Temporal decoupling via events: end the slice at its own state change (“order placed”), let a coordinator dispatch, and model success first, then failure. L18 L82 →
  • George Clooney test: “Who else is going to play this role?” Abstract only when there is more than one actor. Start with an interface, and move to an abstract class only after the rule of three. L79 L84 →
  • Object stereotypes: information holder, structurer, service provider, coordinator, controller, interfacer. Lean into each object's dominant role. Controllers get called; they don't subscribe. L94 L95 →
  • Invariants live in domain objects: private constructor + static create, validation in value objects, expected failures returned rather than thrown. The domain stays pure. L77 L74 →
  • Small aggregates: the minimum data a command needs, which is its transaction boundary. Reference other aggregates by ID. L88 L89 →
  • Own the control center: if you need React to test a feature, React is doing the coordinating. L87 L94 →
  • Default shape: a modular monolith with an event bus. Fewer components means fewer guesses. L71 L84 →

Theoretical Design Checklist (Before Any Code) L65 L88

  1. Who / why / what before how: actor → role → goal → capabilities. Exit when you can say who you help, what they achieve, and why it's worthwhile. L21 L66 →
  2. Concrete examples: start state, end state, what the person does, what they see. L68 →
  3. Subdomains: brain-dump the problem categories and stop when you run out. L66 →
  4. Bounded contexts: group by shared language (“be Aristotle”), classify core / supporting / generic, decide build vs buy, draw the context map. L67 L68 →
  5. Event storm one scenario: past-tense events → imperative commands → actors → aggregates → boundaries. Be wary of same-context event chains. L69 →
  6. Add views and tally the I/O data for each command–event pair. L70 →
  7. State machines: states, transitions, events and invariants. One state change per step, per context. L74 L70 →
  8. Architecture: modules, deployable units, event bus, and tools chosen by responsibility and NFR. L71 L92 →
  9. Go physical: pipeline → E2E in a production-like environment → level-3 tests. L72 →

Anti-Patterns to Catch in Review

Flag these
  • Package by infrastructure (routes/, controllers/), which hides the features. L16 L88
  • Fat controllers / anemic domain: HTTP, rules and SQL in one handler, or this.repo.save in a controller. L84 L93
  • Environment checks everywhere and imports pulled in “willy nilly”. L19
  • Mocks that lie: fakes with no contract tests (“we're only testing our mocks”), or inline library-mock soup. L81 L73
  • Implementation-detail test names such as “sets result to true and error to null…”. L56
  • else-if chains instead of early-return ifs. L47
  • Big-bang commits, commits on red, or design done off-screen in one jump. L46 L63
  • Code-first / DB-first / API-first design: thinking in endpoints, not features. L8 L82
  • Awaited side effects appended to a command: one failure strands the rest (the makePurchase script). L18 L88
  • Components for weeks, deploy last, which ends in “all these weird CORS errors”. L24 L81
  • Premature interfaces: “You George Clooney'd it.” L79
  • Everything is a “service”, and React is the control center. L94 L87
  • E2E-only or unit-only strategies, and state/communication checks at E2E. L87
  • Husky as the only quality gate, or manual walkthroughs as features grow. L25
  • Modelling the domain before the theoretical guesses, or learning DDD on a project with no real value. L65 L93
  • Rewriting legacy code from scratch instead of pinning it with characterization tests first. L81 L92
  • Comments that restate the code. L48

Mindset One-Liners L3 L4

Clarity beats anxiety

Anxiety at work means you lack clarity. Fix your mental models; don't push harder. L89 L4 →

Purpose beats boredom

Tie the work to something that matters. Use the trail of whys until you reach an emotional charge. L4 L6 →

Essentialism loop

Observe & evaluate → eliminate → execute in a straight line. Learn “topics for problems”. L5 L85 L91 →

Think backwards

Name the end state first, then let it “carve the pieces moving back”. This is the idea behind TDD. L75 L3 →

Right action

At quantum moments (“how do I start this project?”) you act on what you value. Value code and you get code; value value and you get value. L85 →

Refinement

Is it working and doing what we need? Then move on. Kill your designs and design it twice. L3 L63 →

No more “it depends”

Run the scenario: theoretical → physical → which guesses → time budget. That's what it depends on. L91

Zoom out when stuck

Stuck in a change-fail loop? Stop, draw it, clarify the responsibilities, then descend one level. L82 →

Using This with AI Coding Agents Added by Copilot

The course's own take: AI “crunches down” some state-change and decision logic, and the skill left to you is knowing the inputs, outputs and goalpost L89. The first milestone had ChatGPT write the code from a pasted grading checklist L42. The checklist below maps the course frameworks onto how you spec and review agent output.

AI-era lens · Copilot
  • Spec = Find output. Give the role, goal, feature, acceptance criteria and a concrete-examples table. A vague prompt is vagueness that won't compile. →
  • Add Architect + Automate. Name the guess point, the subject under test, the contracts it may depend on, the target folder (modules/<capability>/<feature>) and the exact test command.
  • Demand tests first, AAA-backwards. One example per loop, named as responsibilities. Check that the test fails for the right reason before accepting any code.
  • Ask for red-green-refactor commits labelled as new functionality or refactor, so you review a story of commits and not a big-bang diff.
  • Review with the kata checklist and the anti-pattern list. Else-if chains, what-comments, fake names and premature interfaces are common in generated code. →
  • Guard layer boundaries. No new Date() or Math.random() in the domain, no repo calls in controllers, no environment checks outside the composition root. Consider enforcing this with architecture tests (the course mentions TS-Arch L68).
  • Every generated fake needs a contract test. Reject mocks of your own roles that have no parity with the real implementation.
  • Keep the theoretical guesses human. An agent can draft an event storm, but only users and domain experts validate value, and KPIs close the loop.
