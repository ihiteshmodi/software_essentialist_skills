How to Do Kata Assignments L43 L44 L52

  1. One branch per attempt — use the pattern <project>-<date>-<iteration>. You can redo the kata several times, even on the same day, and each attempt has a single URL to share for feedback. L43
  2. Use the grading checklist as your spec — Khalil copies it straight into the test file to start. L45 L42
  3. Map the problem to input → output before coding. A stateless guess point is “data in, data out.” L46
  4. Loop red → green → refactor, one example per loop, committing at the points shown in the diagram. L44 L49
  5. Open a pull request so reviewers can comment inline. Reviews read the end result first, then walk back through the commits. L46 L47

Rules of the stateless guess point (as enforced in the reviews)
  • Data in, data out. The SUT is a function or a static method on a stateless class. Don’t instantiate it. L52 L54 L56
  • Red for the right reason. A missing function or import is a compile failure. Export a stub and import it first, so the test fails on logic. L45 L49
  • Simplest transformation to green. Fake it until you see duplication three times. Obvious implementation is allowed when you’re confident. L45 L47 L60
  • Rule of three. Ignore duplication in red and green. Refactor it only on the third occurrence, and never add examples during a refactor. L45 L52
  • One example at a time. Several examples at once force more complex transformations and give unclear failures. L49 L55 L62
  • Refactor XOR transformation. A step does one or the other. L49
  • Refactor the tests too, not just production code. L45
“You only want to commit on red when you're in red for the right reason.”L49

Agents default to the obvious implementation and batch several tests together. Ask for one failing test, then “the smallest fake-it change that makes only this test pass,” and commit before the next prompt. Your commit history then shows the red → green → refactor path, and each AI diff stays small enough to review.

First Milestone: “Just Make It Work” Backend API L42 L86

Problem: build three user use cases for DDD Forum as a RESTful API. The grading checklist asks for (1) three routes: POST /users/new, edit user, get user by email, (2) a relational or NoSQL DB, (3) an optional ORM (TypeORM / Prisma), (4) manual verification with Postman or curl. Khalil used Express + TypeScript + Postgres + Prisma, and ChatGPT wrote most of the code from the pasted checklist. L42

  1. Prompt — “generate the code needed to build an MVC RESTful API with Express.js, Prisma, TypeScript, and Postgres, with the following API endpoints…”, with the grading checklist pasted in. L42
  2. Paste & fix — install @types/express, move the misplaced prisma/ folder, delete the generated app.ts, delete the redundant models/user.ts (the Prisma client already provides the types), fix a string→number id error. L42
  3. Fight the environment — Postgres via Homebrew, a “failed to create user” error surfaced with try/catch, a DATABASE_URL mismatch fixed with createdb, then npx prisma db push. L42
  4. Verify by hand — curl create → edit (John → Jonathan) → get by email. L42
Why it’s messy (on purpose)
  • Fat functions wired straight to Express. Basic functions act as “pretty much the entire service layer,” connected directly to controllers. HTTP, validation and Prisma calls all live in one handler. L42
  • Blind copy-paste (“pretty brainless on my part”) led to wrong folders, a duplicated model and type errors. L42
  • DB installed on the machine, not in a container. Docker and idempotency are deferred to Best Practice First. L42
  • No automated tests. Verification is manual curl, and a lot of time goes into debugging. L42

Where this code goes later: splitting the fat handler into a use case behind a repository contract is covered in Horizontal Decoupling. The katas below practise the other half first: the smallest, stateless unit, test-driven.

Context from the “First Milestone Review” Q&A

Despite its title, the session reviewed no milestone code. It pointed students to FA²STR at the stateless guess point and explained that FA²STR is an input → output tool usable at any level of abstraction. Wherever a problem starts (stateless, stateful, application, E2E), you “drill in with several loops,” which Lucas summed up as n loops rather than a fixed nth layer. L86

“Writing code is not the hard part. It is all of the other aspects of writing code, the design, testing, architecture, and strategy parts.”L42

Palindrome L49 L50

Problem: detect palindrome words (mom and wow are palindromes, bill is not) and phrases (“Was it a rat I saw?”, “Never odd or even”), plus the grading-checklist examples. L49 Trains: the micro-mechanics of red-green-refactor, which matter much more at higher guess points (outgoing adapters, E2E). L49

Before — red for the wrong reason, two tests at once, a transformation mixed with a refactor L49
After — each commit is one phase, one example, one kind of change
Before — double negative: hard to parse
After — positive, concrete “knows that …” names

Review #2 L50: the final tests read well (describe + it.each for palindromes, including books, movies and places; non-palindromes; non-strings that throw). The mechanics were off. The student started with a fake implementation before any red. The second commit was too big (“normalize to lowercase, reverse it, compare it” plus all the examples). Commit messages had no phase labels, and there was an unnecessary comment. Verdict: redo the kata with strict red/green/refactor commits. The student also asked whether the solution was a pure function:

Before — “functional, but not a pure function” by Khalil’s definition: const introduces state
After — pure by his framing: no declarations, just a pipeline of functions

Added by Copilot This is Khalil’s stricter definition. Many FP references treat local immutable bindings as compatible with purity. The review’s practical point stands either way: no side effects means an input/output system.

Commit-size trade-off

“How much complexity can you tolerate?” One example per commit is slower but simpler. Many at once is faster but more complex. Default to one, because FA²STR at the next guess points will require it. Put the “throws when not a string” feature in its own commit. L50

Comments

“That comment is unnecessary. So get rid of that.” Code says what. Comments are a last resort, used only for why. L50 L48

Password Validator L54 L55 L56 L57

Problem: a function or stateless class that validates passwords. They must be 5–15 characters, contain at least one digit, and contain at least one uppercase letter. It returns an object with a boolean result and an errors key listing every error that occurred. L54 Trains: FA²STR (upfront + emergent), AAA backwards, program by wishful thinking. L56

Upfront design: Find → Architect → Automate L54 L52

Find

Read the problem. Write success and failure examples for each criterion in a “find” file. Classify the requirements: one doing (validate password) and many knowings (5–15 is valid, no digit is invalid, …). The knowings become most of the tests. Sketch the output for an input that breaks every rule ("s"). L54 L52

Architect

Get clear on the system under test: string in, object out, through a stateless class with a static method or a plain function. At the stateless level this step is “extremely simple.” L54

Automate

Set up the test infrastructure. Here that’s just Jest. All of this can happen “in a millisecond” in your head. Writing it down makes the metacognition visible. L54

Emergent design: Specify → Test → Refine (commit on green only) L55

  1. Valid password — written backwards (assert → act → arrange). result.result read badly, so the variable became output. Fake it: return { result: true, errors: [] }. Commit.
  2. Invalid length — expect exactly one error. errors became its own array, with an “is between 5 and 15” check that pushes InvalidLength. Commit.
  3. Another length example — passes immediately. Commit.
  4. Refine — length examples go into an it.each table (input, expected result, expected errors) nested under a describe naming the behavior. Commit.
  5. Digit feature — the success example passes immediately. The failure example drives hasDigits. A copy-pasted test still expected a truthy result and was fixed. The next example passes. The feature is refined into it.each the same way.
  6. Detect multiple errors — a feature only implied by the statement (“read between the lines”). The expected errors were deliberately listed in a different order from the push order. toStrictEqual failed, and the fix was per-error toContain.
  7. Stopped before the uppercase feature (“pretty much just typing”).
Levels of abstraction in a test file

Specification (feature/responsibility name) → concrete examples → test code → production code. “You always have a higher level of policy that's describing what is happening.” L55

Review feedback → fixes

Before — instantiating a stateless class; the test name describes how (keys, flags, null) L56
After — static call; the name states a responsibility (“can … / knows that …”), the how stays in the body
Before — hard-coded reason copied across tests: the “too long” tests still said “too short” L56
After — encapsulate what varies: password + reason in one row, substituted into the name and the assertion
Before — order-dependent assertion couples the test to push order in production L55
After — assert containment: “I don't really care about the order”

Review #2 (Tim) L57 was mostly praise. It used a plain function (the closest to essential complexity), a fake-it first commit, tiny transformations and toContain (“a very good API”). It also strictly typed the response, which turns the return shape into a role:

Breadth triangulation

One concrete example per responsibility, then move to the next feature. Tim did this. Adding the uppercase test forced him to update older inputs so they kept passing. L57

Depth triangulation

One feature, with more and more examples to strengthen its abstraction. Both styles are valid. L57

Next step for Tim

Near-duplicate standalone tests → it.each rows of input + expected errors, then many more combinations. Name multi-error tests precisely: “missing digit and missing uppercase letter.” L57

“You want to decouple the how from the what. That's huge. Because the how could change. But you still want the what to stay exactly the same.”L56

Stats Calculator L58 L59

Problem: process a sequence of integers and report statistics on them (e.g. minimum and maximum). The what is fixed. The how (return an object, a string or an array) has many valid answers, and “that is a key distinction.” L58

Clarify before you verify (new Find-step principle)
  1. List the responsibilities from the description.
  2. List concrete examples.
  3. Decide the output data structure (object / string / array) and strictly type it.
  4. Decide how you’ll verify each responsibility.

The reviewed student did this in the first commit: calculateStats(numbers) returns a typed stats shape. The commits then showed baby steps. L58

Before — firstInput / secondInput / thirdInput hide which edge case each covers; the tests repeat L58
After — named example sets + it.each: the intent is readable, and each example lives in one place
Before — inputs and expectations in separate structures; the spec names the return shape (how) L59
After — one object per example + responsibility specifications (a doing or a knowing)
Responsibility specification vs examples

A test spec has two parts. Responsibility specifications name a doing or a knowing (“it can calculate the minimum value”) and stay abstract. Examples are as concrete as possible. Drive with concrete examples, and end up with abstract responsibility specs. L59

Refinement budget

“You could spend so much time refactoring these examples.” Refine until the tests are readable, then stop, but never trade away readability. Parameterizing is now a grading-checklist refinement. L59 L58

“Names are not something to be wasted. Names actually do a lot.”L58

Military Time Validator L60 L61

Problem: given a string that may be a valid or invalid military time range (e.g. "01:12 - 14:32", format inferred), write a function or stateless class that detects which. Trains: picking the simplest transformation with the Transformation Priority Premise, here and in the Boolean Calculator. L60

Transformation Priority Premise (simplest first) L60

  1. nil — return nothing. Fake it can start here so the first test fails for the right reason.
  2. constant — return a hard-coded value.
  3. combine constants — e.g. add two constants.
  4. scalars / arguments — use the input.
  5. single statement — one functional expression calling functions or “service providers” such as min/max.
  6. conditional + return — multiple statements.
  7. more conditionals, more statements — variables and mutation sit here, at the costly end.
Using TPP
  • Use it at FA²STR’s Test step (keep the obvious implementation at the simplest option every time) and at the Refine step. L60
  • “If you feel like you need to add a variable or you think you need to do some mutations, question your transformation.” L60
  • For reference, a condition-map abstraction on test one sits around “level seven or eight.” L63

Review #1 (Loki): functional decomposition, commit by commit L60

“Some of the most readable commits in a story of commits” Khalil had seen. The problem was decomposed down to the tiniest responsibility and composed upward:

Before — one function doing everything: a mutable flag and nested branches (high on the TPP list)
After — tiny responsibilities composed upward; helpers encapsulated by not exporting them
Before — “revise index file for clarification” added comments that restate the names L60
After — delete them: the names already say what. “Do we really need comments? I wouldn't say we do.”

Review #2 (Kareel): class-based, “an exemplary demonstration” L61

Commit story: fake a basic valid example → a falsy example (hour 25) forces parsing → refactor “group test by validity” → hour bounds with isHourValid → minute checks → refactor merging the helpers into one isTimeValid + parseTimeRange → a finite-number check → start must be before end (several examples had to change). L61

Before — a copied test per example: each new case duplicates structure (closed to extension) L60
After — responsibility spec → parameterized examples: “super open closed”, so a new case is just a new row
Levels of abstraction, highest → lowest
  1. You explaining the problem out loud to someone.
  2. The specifications.
  3. The test code.
  4. The first level of production code: the function or static method that kicks off the SUT, reading as the algorithm’s steps.
  5. Encapsulated lower-level helpers, seen only when you “descend a layer deeper.”

“That sort of gradient like movement from theoretical to physical.” L61

Functional vs OOP encapsulation: functional code co-locates state and behavior in one file and hides helpers by not exporting them. OOP encapsulates them together in a class. L60 Kareel’s class had to be instantiated. A static method would also work, which is “not a huge deal.” L61

AI-era lens · Copilot

TPP gives you a shared vocabulary for keeping AI diffs small. Try “make this test pass using the highest-priority transformation on the TPP list: constant before conditional, no new variables.” If the diff introduces a let, a loop or a lookup map for one new example, reject it and ask again one rung lower.

Boolean Calculator (Design It Twice) L62 L63

Problem: evaluate a boolean expression given as a string, such as "TRUE", "FALSE", NOT, "TRUE AND FALSE", and later parentheses. It has “one other aspect” that makes it harder than Military Time. Khalil flagged it as a kata that may need upfront design. L62 L63 L60 L54

Johan: emergent, swim lanes L62

“One of the best ones I've seen so far.” Tests are grouped into describe swim lanes (incorrect input, TRUE/FALSE, NOT, AND), which is categorical thinking, so it’s obvious where the next test goes and you can triangulate within a lane. Transformations are simple. Trouble starts at AND: two tests in one loop, deeply nested describes, and vague words (“parts”, “one/two/three”).

Shannon: upfront, one big guess L63

All tests pass, but the first commit already had describe.each table infrastructure plus a “condition map”, a stack, tokens and operands. That’s an upfront design decision (FA²STR’s Architect), “five, six, seven different guesses all at the same time.” The design lives in the author’s head, not in commits a reviewer can follow.

Johan’s sequence L62

  1. Invalid input → throw — obvious implementation, “a great first defensive coding commit.” Rename the context to “when input is not correct.”
  2. TRUE → return true — the simplest thing, even with foresight. “Lead with the guess.”
  3. FALSE — evaluate the condition inline instead of adding an if.
  4. NOT — “input includes NOT”. Similar code appeared twice, so no refactor yet (rule of three).
  5. AND — two tests at once (flagged). Split on AND and require every token to be true. A refactor introduced transformValuesToExpression, and words like values and expressions began to appear.
  6. TRUE AND NOT TRUE — checkNegation works, but the test name was hard to read.
Before — conditions encoded as nested describes: high “psychic entropy” for the reader L62
After — lead with the concrete example. “It's always going to be easier to just use an example.”
Before — an if adds a statement and a branch (lower on the TPP list)
After — evaluate the condition inline: one expression, the simpler transformation
Before — test one arrives with table infrastructure and a condition map: TPP “level seven or eight” L63
After — “take one example, write it as English, make that your it statement”; production starts at return true
Design it twice

Once you have a working upfront solution, redo it and arrive at the same place emergently, one guess at a time (from A Philosophy of Software Design). “Allow the tool to be doing the heavy lifting, which is to make the small guesses and lead with that.” For stateless problems, start with plain it tests and refactor toward describe.each/it.each later. L63

Name the concepts (ubiquitous language)

“What is a part really?” A part, a token, a value, an expression? Name the concepts instead of numbering them, and refactor test names for meaning too. Pushing complexity into deeper layers is fine: “That complexity needs to go somewhere and it's essential.” L62

Both reviews end positively. Shannon’s code “looks really elegant”, and nested statements get refined in the later stateful sections, not here. It’s a spectrum: if you’re confident and short on time, the whole thing can be an obvious implementation. L63

“All of what is happening here is happening within your brain. It's not happening within the code to be read as a story.”L63
